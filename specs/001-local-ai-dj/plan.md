# Implementation Plan: Local AI DJ v2

**Branch**: `001-local-ai-dj` | **Date**: 2026-04-15 | **Spec**: [spec.md](./spec.md)

## Summary

A self-hosted AI DJ web application with Kokoro TTS (on-device), Ollama LLM (local), audio crossfade mixing via ffmpeg, real-time browser UI with visualizer, PWA for Android, song requests, mood-based playlist generation, and persistent listener stats. Server mixes audio server-side and streams as continuous HTTP audio; WebSocket handles real-time state sync across all clients.

## Technical Context

**Language/Version**: Python 3.11 (backend), TypeScript / React 18 (frontend)  
**Primary Dependencies**: FastAPI, kokoro-onnx, pydub + ffmpeg, mutagen, watchdog, httpx (Ollama), SQLite + SQLAlchemy, Vite + TailwindCSS + shadcn/ui, vite-plugin-pwa (Workbox)  
**Storage**: SQLite (library index, stats, playlists, queue)  
**Testing**: pytest (backend), Vitest (frontend)  
**Target Platform**: Linux server (local + remote), Chrome/Firefox/Safari browsers, Android PWA  
**Project Type**: Web (backend + frontend)  
**Performance Goals**: TTS generation < 3s, library scan 1k tracks < 30s, audio stream latency < 500ms  
**Constraints**: No outbound internet after setup, all AI runs on-device, single SQLite file for portability  
**Scale/Scope**: Single household, 10k+ track library, 2–10 simultaneous browser sessions

## Constitution Check

- ✅ Single responsibility: backend handles audio/AI, frontend handles UI
- ✅ No over-abstraction: direct SQLite via SQLAlchemy, no ORM ceremony
- ✅ Config-file driven: all tunables in `.env` / `config.yaml`
- ✅ Graceful degradation: Ollama down → template fallback; TTS fail → silent transition
- ✅ PWA via service worker; no native app packaging required

## Phase 0: Research

### Audio Streaming Architecture Decision
- **Decision**: Server-side continuous audio stream via HTTP chunked transfer (`/stream` endpoint), server mixes music + TTS using pydub + ffmpeg subprocess. Client plays via `<audio>` element.
- **Rationale**: Simplest cross-browser compatible approach; browser `<audio>` handles buffering; no MSE complexity needed for v1.
- **Alternatives considered**: Web Audio API client-side mixing (complex cross-browser sync), Icecast (extra dependency).

### TTS: Kokoro ONNX
- **Decision**: `kokoro-onnx` Python package — runs ONNX-exported Kokoro model on CPU/GPU.
- **Rationale**: ~500MB model, fastest inference among high-quality local TTS, Apache-licensed, simple Python API, no server required beyond the backend process.
- **Model**: `kokoro-v1.0` — 82M parameters, supports American/British English voices.

### LLM: Ollama
- **Decision**: Ollama REST API (`http://localhost:11434`) via `httpx`. Default model: `llama3.2:3b` (fast, low memory).
- **Rationale**: Already common in the user's homelab; 3b model generates commentary in < 2s on CPU.
- **Fallback**: Jinja2 template strings with `{artist}`, `{title}`, `{genre}` substitution.

### Crossfade Mixing
- **Decision**: `pydub` + ffmpeg CLI for audio segment manipulation. Crossfade = overlap last N seconds of track A with first N seconds of track B using volume envelope.
- **Rationale**: Handles all audio formats via ffmpeg; pydub provides simple Python API for slicing and mixing.

### Real-time Sync
- **Decision**: FastAPI WebSocket `/ws` endpoint broadcasts state events (track change, queue update, request acknowledged) as JSON.
- **Rationale**: Native FastAPI support, works well with React state management.

### PWA
- **Decision**: `vite-plugin-pwa` with Workbox. Manifest with `display: standalone`, `theme_color`, icons.
- **Rationale**: Zero-config PWA generation; Workbox handles service worker caching strategy.

### Database
- **Decision**: SQLite via SQLAlchemy 2.0 ORM. Single file `data/dj.db`.
- **Rationale**: No external DB server, portable, sufficient for household-scale use.
